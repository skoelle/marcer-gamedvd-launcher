# Marcer GameDVD

Tools and apps for browsing and launching the [Marcer GameDVD](https://www.facebook.com/groups/360493904888475/) Atari ST game archive.

The primary application is the **Flutter desktop app** — a gallery-style inventory browser with metadata, screenshot previews **and Marcer's curated box scans & manuals**. A legacy **console launcher** (C#) and a set of Python maintenance tools round out the monorepo.

---

## 🗂️ Applications

| App | Path | Tag | Description |
|---|---|---|---|
| **Desktop app** (primary) | [`apps/marcer_desktop`](apps/marcer_desktop/README.md) | `desktop-v*` | Flutter desktop app: gallery-style catalog grid, game info, screenshots, lightbox, **Marcer's curated box scans & manuals**, optional folder browser. |
| Console launcher (legacy) | [`apps/marcer_console`](apps/marcer_console/README.md) | `v*` | Keyboard-driven terminal UI over the same archive; launches ZIPs in Hatari. |

Both are strictly **read-only** consumers of the archive and its derived artifacts.

## 🖥️ Desktop App (Flutter)

**Browse the whole GameDVD archive like a gallery — screenshots, metadata and a
full-screen viewer, driven entirely by the keyboard.** It is a windowed
master-detail browser (Surface A; a fullscreen couch mode, Surface B, is
planned) built with Flutter, and a strictly **read-only** consumer of the
archive and its derived artifacts — except `favorites.txt` and, on explicit
Save, the manual screenshot curation described below.

![Catalog grid with filters and detail sidebar](docs/images/catalog.png)

![Gallery lightbox with variant filmstrip](docs/images/lightbox.png)

### ✨ Features

- **Gallery-style catalog grid** with section tabs (`games`, `pd`, `utils`,
  `magazines`, `falcon`, `crews`), search, status/publisher/crew/cracker/
  language/year/genre/developer filters, tri-state `raw`/`pasti`/`boxscan`,
  `TOS/Bad` and a combined sort dropdown. Every dropdown is virtualized and
  type-to-filter.
- **Detail sidebar and full-screen lightbox** with the "This ZIP" table
  (including the release-specific `Cracked by`/`Crew` taken from the XLS row
  that matches the selected ZIP; missing labels fall back to the ZIP-name
  inference in `crews.json` and are marked `inferred`), release variants, a
  variant filmstrip, candidate strip, integer-scaled images and clickable
  previous/next navigation. XLS placeholders (`Original`, `Unknown`, …) are
  never shown as a cracker/crew.
- **Marcer's curated box scans & manuals** — see below.
- **Optional AtariLegend metadata** (genre, developers/roles, boxscans,
  screenshots, reviews, magazines, comments, community score) and the optional
  **Pete Clarke PirateFinder catalog** (catalogue facts, crew histories,
  menu-disk appearances, trivia), both downloaded on demand, never bundled
  (CC BY-NC-SA 4.0). PirateFinder matches use the precomputed disk-image
  hashes from `full-index.json.gz` (exact) with a title fallback.
- **Crews tab** from `crews.json` with a release browser (game title, folder
  buttons and lightbox-style badges for the selected release, plus a cracker
  filter built from the crew's releases) and PirateFinder
  crew details. Joint credits use the unified `A & B` spelling and stay their
  own group unless explicitly allowlisted for merging.
- **Local layer & missing ZIPs** resolved from the filesystem
  (`ROOT`/`PATCH`/`BOTH`, `MISSING`), plus **Download folder** from the Marcer
  FTP for absent game folders.
- **Launch with Hatari** (`P`/`Space`/Play) with Standard/Mono/STE/Low-Res TOS
  variants, Falcon 030 titles and GEMDOS magazine cover disks; optional
  **Send to CosmosEx**.
- **Favorites** per section, manual screenshot curation (`M`/`C` + Save),
  on-demand **Hatari/TOS install**, **self-update**, and graceful degradation
  when artifacts are missing.

The complete behavior is specified in
[`docs/specs/SPEC-desktop.md`](docs/specs/SPEC-desktop.md).

### 📸 Screenshots: actual ZIP boot state, not AtariLegend

The `screenshots-*.zip` archives published on the Marcer FTP (generated by
`tools/screenshot-gen`) deliberately do **not** use AtariLegend images. They
capture the actual state of each ZIP/floppy image as it boots:

- A ZIP may show a game, a crack intro, the TOS desktop, a text screen or no
  usable image at all — that is its real boot behaviour, not a curated game
  shot.
- Every release/crack variant gets its own preview and candidates, so
  differences between the ZIP variants remain visible.
- The previews therefore often show loaders, desktops or text screens instead
  of in-game graphics. This is intentional.

For curated in-game screenshots, connect the optional AtariLegend data
locally (**Settings → AtariLegend data → Download AtariLegend data**).
The AtariLegend dialog then shows AtariLegend's own hotlinked screenshots and
boxscans, separate from the boot-state previews in the catalog grid and
lightbox. AtariLegend data is downloaded at runtime, never bundled, and is
CC BY-NC-SA 4.0 (see [License](#license)).

### 📦 Marcer's curated box scans & manuals

The archive's hand-curated `Boxscan/` and `Manual/` folders are a first-class
feature: `Box scans (N)` / `Manuals (N)` chips open a per-edition gallery and
full-screen viewer, or the grouped manual list (scan/text PDFs, image-page
manuals, `.msa` as info-only disk images). Assets are discovered lazily for the
selected card, both layers are merged, and nothing is ever modified or bundled.

Details: [`docs/specs/SPEC-desktop.md`](docs/specs/SPEC-desktop.md#box-scans--manuals)
and [`docs/analysis/ANALYSIS-boxscan-manual-assets.md`](docs/analysis/ANALYSIS-boxscan-manual-assets.md).

### 🚀 Quick start

1. **Download** the ZIP for your platform from the
   [Releases](https://github.com/skoelle/marcer-gamedvd-launcher/releases) page
   and extract it.
2. **Run** `MarcerGameDVDLauncher` (`MarcerGameDVDLauncher.exe` /
   `MarcerGameDVDLauncher.app`).
3. **Set up your paths** in the first-run **setup page** (shown automatically
   when no `desktop.config.json` exists): fill in the paths, watch the live
   ✓/✗ per field, and **Save** — the config file is written next to the
   executable (macOS: next to the `.app`) and the app continues into the
   catalog. See *Configuration* below.

Alternatively, copy the shipped `desktop.config.example.json` next to the
executable (or the `.app`), rename it to `desktop.config.json`, and edit it by
hand before the first start.

For the quick start and the complete release walkthrough — including macOS
Gatekeeper/translocation notes, `ftp-sync` game/patch directories, FTP settings
and the catalog-data downloads — see
[`docs/guides/GETTING-STARTED.md`](docs/guides/GETTING-STARTED.md).

### 📥 Download

Download the ZIP for your platform from the [Releases](https://github.com/skoelle/marcer-gamedvd-launcher/releases) page:

| Platform | Archive |
|---|---|
| Windows | `MarcerDesktop-*-win-x64.zip` |
| Linux | `MarcerDesktop-*-linux-x64.zip` |
| macOS | `MarcerDesktop-*-osx-arm64.zip` |

**Minimum requirements:** Windows 10/11 (64-bit; the ZIP includes the Visual
C++ runtime), Ubuntu 24.04 LTS+ (64-bit, GTK3), macOS 12 Monterey+ on Apple
Silicon. Intel Macs are not supported.

The release ZIPs ship `desktop.config.example.json` **and** the bundled
`MarcerGameDvd-Hatari.cfg` — copy the example next to the executable (or the
`.app`), rename it to `desktop.config.json`, and set your absolute paths. For
launching, point `Hatari.Executable` at your Hatari binary (or use the in-app
**Install Hatari…** to download prebuilt Hatari 2.6.1 on Windows/macOS). If
`TOS.IMG` is missing, the app offers to download it (TOS 1.04, English (UK) or
German) from atariworld.org and install it next to the app (the STE, Low Res
TOS 1.02 and Low Res TOS 1.00 Play variants download TOS 1.62 / 1.02 / 1.00 on
demand).

> **macOS:** the build is ad-hoc signed and not notarized, so macOS quarantines
> the download. Extract the **whole ZIP** into a normal folder under your home
> directory (e.g. `~/MarcerGameDVDLauncher/`) and keep the `.app`,
> `desktop.config.example.json` and `MarcerGameDvd-Hatari.cfg` together; start
> the app from there. Open it once via **right-click → Open**, or run
> `xattr -dr com.apple.quarantine /path/to/MarcerGameDVDLauncher.app`. Do not
> run it from Downloads/Documents/Desktop or directly from the ZIP. If macOS
> still runs a translocated read-only copy (app hint or self-update failure),
> clear the quarantine or re-extract/move the app to a different normal folder.
> The app is not sandboxed (it reads game folders you configure and launches
> Hatari); protected folders like `~/Downloads` still trigger a one-time macOS
> permission prompt. See
> [`docs/specs/SPEC-desktop.md`](docs/specs/SPEC-desktop.md#macos).

### ⚙️ Configuration (`desktop.config.json`)

The app searches the current directory, the executable directory and (macOS) the
folder containing the `.app` plus `~/Library/Application Support/MarcerGameDVDLauncher`;
a new config is written to the first writable location. Without a config the
first-run setup page opens. The ⚙ settings editor edits all paths, FTP and
CosmosEx fields, validates them live and reloads the catalog in place.

Field reference and the complete setup walkthrough:
[`docs/guides/GETTING-STARTED.md`](docs/guides/GETTING-STARTED.md). Template:
[`apps/marcer_desktop/desktop.config.example.json`](apps/marcer_desktop/desktop.config.example.json).

### ⌨️ Keyboard shortcuts

| Key | Action |
|---|---|
| `↑` / `↓` | Move the selection (one row in grid view) |
| `←` / `→` | Move the selection left / right (grid) |
| `Home` / `End` | First / last card (grid) |
| `PgUp` / `PgDn` | Jump one page up / down |
| `Enter` / `→` | Open the folder / show the lightbox |
| `Backspace` | Parent directory (in catalog view: clear filters) |
| `*` | Toggle favorite on the selected ZIP / catalog card (for a card: its single starred variant, else the launch ZIP; also in the detail panel and on the lightbox's shown variant / filmstrip star) |
| `M` | Lightbox only, on a candidate image: swap it with the variant's main image (`<base>.png`) |
| `C` | Lightbox/detail view: change the shown ZIP's status/kind (pending until **Save (n)**) |
| `P` | Launch the selected ZIP with Hatari |
| `/` | Focus the search field |
| `T` | Toggle catalog grid / folder view |
| `?` | Show the help overlay |
| `ESC` / `q` | Exit (in the lightbox/dialogs, `ESC` closes that view) |

The same help overlay opens via the question-mark button in the top-right
toolbar, left of the settings gear.

In the **lightbox**: `←`/`→` switch card (clickable arrows sit outside the
lightbox at the left/right with the neighbour title when the window is wide
enough; arrow only when space is tight, hidden at the first/last card and
when the window is too narrow), `↑`/`↓` switch variant, `PgUp`/`PgDn`
switch image, `Space`/`P` launch the shown ZIP (the favorited ZIP of that card
when exactly one variant is starred), `*` favorite the shown variant (or click
a filmstrip star), `M` make the shown candidate the main image, `C` edit
status/kind, `?` opens help and `Esc` closes. Clickable controls: filmstrip
thumbnails/stars, candidate strip, AtariLegend, `Box scans`/`Manuals` chips,
and the ROOT/PATCH folder icons (open the game folder).

> **Manual curation & shotgen compatibility** — `M` is an immediate file swap
> (no index write; names never change). `C` changes stay in memory until the
> **Save (n)** button writes them atomically (tmp + rename) while holding the
> `shotgen.lock` PID lock; a live screenshot-gen run blocks the save. Entries
> saved as `done` are never touched by later shotgen passes; `desktop`
> entries can still be re-classified by `shotgen reclassify` (which re-reads
> the preview image) — pick `done` when a manual kind should stick.

> **Launching** needs `Hatari.Executable` in `desktop.config.json` and a TOS ROM
> (`TOS.IMG`) next to the app — same convention as the console launcher; the
> bundled `MarcerGameDvd-Hatari.cfg` looks for it in the working directory. If
> `TOS.IMG` is missing, the app offers to download and install it (TOS 1.04,
> English (UK) or German) from atariworld.org; the STE, Low Res TOS 1.02 and
> Low Res TOS 1.00 Play variants download TOS 1.62 / 1.02 / 1.00 on demand.

### 🛠️ Build & Run (developers)

Requires the Flutter stable SDK in `~/flutter` plus the Linux desktop toolchain (`clang cmake ninja-build pkg-config libgtk-3-dev liblzma-dev`).

```sh
export PATH="$HOME/flutter/bin:$PATH"
apps/marcer_desktop/run.sh                      # run app (linux desktop)
cd apps/marcer_desktop/packages/marcer_catalog && dart test   # data-layer unit tests
cd apps/marcer_desktop && flutter test          # app unit tests
cd apps/marcer_desktop && flutter analyze       # lint
```

`run.sh` seeds a git-ignored `desktop.config.json` from `local/paths.env` on first start.


## 🔧 Tools

Helper tools for maintaining and enriching the game archive (not part of either app's release ZIP). Python scripts run via their `run.sh` wrapper with the repo `.venv`; paths come exclusively from the git-ignored `local/paths.env`.

| Tool | Purpose | Docs |
|---|---|---|
| [`tools/gameinfo-gen`](tools/gameinfo-gen/README.md) | Extracts game metadata (publisher, cracker, year, language, dump flags, …) from the GameDVD XLS workbooks into JSON under `MARCER_DATA_DIR/gameinfo`. | [`tools/gameinfo-gen/README.md`](tools/gameinfo-gen/README.md), [`ANALYSIS-game-data.md`](docs/analysis/ANALYSIS-game-data.md) |
| [`tools/archive-sync`](tools/archive-sync/README.md) | Headless FTP archive sync into `MARCER_PATCH_DIR` (root is read-only): size-based change detection, parallel directory listing, atomic downloads, `changes.json`/`changes.txt` reports; no persistent state; never deletes local files. Replaces the interactive `ftp-sync` workflow for automation. | [`tools/archive-sync/README.md`](tools/archive-sync/README.md), [`PLAN-docker-pipeline.md`](docs/plans/PLAN-docker-pipeline.md) |
| [`tools/catalog-update`](tools/catalog-update/README.md) | One-shot local catalog pipeline: FTP sync, then `gameinfo-gen`, `full-index-gen` and `crew-analysis` only when their inputs changed. Publishes the gameinfo asset only when its content signature changed or a previous upload/manifest update is pending. Root stays read-only; no rename detection or deletion. | [`tools/catalog-update/README.md`](tools/catalog-update/README.md), [`PLAN-docker-pipeline.md`](docs/plans/PLAN-docker-pipeline.md) |
| [`tools/asset-publish`](tools/asset-publish/README.md) | Packages the catalog data into deterministic ZIPs. Currently gameinfo only: `<MARCER_DATA_DIR>/gameinfo` → `gameinfo-<yyyyMMdd-HHmmss>.zip` in `MARCER_DATA_DIR`, with a content signature that skips unchanged runs (`--force` repacks). Optional `--upload` stores the ZIP directly under its final name on `MARCER_FTP_ASSETS_REMOTE` with a size check (the Marcer FTP allows neither rename nor delete) and then updates `latest.json` via `tools/asset-manifest`; failed uploads/manifests are retried without repacking. | [`tools/asset-publish/README.md`](tools/asset-publish/README.md), [`PLAN-docker-pipeline.md`](docs/plans/PLAN-docker-pipeline.md) |
| [`tools/crew-analysis`](tools/crew-analysis/README.md) | Ranks cracked-game crews/scene groups by direct Disk-1 release ZIPs (crew view) by joining the `Crew Sorted` tree, `full-index.json.gz` and `games-cracked.json`; disk-2+ entries are excluded. Writes ranking + audit files to `local/crew-analysis/` and suggests cracktro card images (`images`, pHash clusters seeded into `crew-images.json`). The ranking no longer depends on the screenshot index. | [`tools/crew-analysis/README.md`](tools/crew-analysis/README.md), [`ANALYSIS-crews.md`](docs/analysis/ANALYSIS-crews.md) |
| [`tools/full-index-gen`](tools/full-index-gen/README.md) | Builds the screenshot-independent catalog index `gameinfo/full-index.json.gz` from the game trees alone: every ZIP with section, layer, size and per-member disk-image hashes (SHA-1/SHA-512/CRC32+size) plus a container fingerprint. Incremental (only new/changed ZIPs are hashed). Ships with the gameinfo asset, so new ZIPs reach the desktop app immediately, even without screenshots. | [`tools/full-index-gen/README.md`](tools/full-index-gen/README.md), [`PLAN-docker-pipeline.md`](docs/plans/PLAN-docker-pipeline.md) |
| [`tools/gallery`](tools/gallery/README.md) | Interactive gallery webapp over the screenshot archive (`MARCER_OUT_DIR`) joined with game metadata (`MARCER_DATA_DIR/gameinfo`), the Crews tab from optional `crews.json`/`crew-images.json`, and optional metadata-only boxscan/manual counts from `MARCER_ROOT_DIR`/`MARCER_PATCH_DIR`. | [`tools/gallery/README.md`](tools/gallery/README.md), [`SPEC-gallery-webapp.md`](docs/specs/SPEC-gallery-webapp.md) |
| [`tools/asset-manifest`](tools/asset-manifest/README.md) | Lists the newest `screenshots-*.zip` / `gameinfo-*.zip` on the Marcer FTP (read-only: connect + list, never uploads) and publishes a `latest.json` pointer as a GitHub release asset on the fixed `catalog-latest` prerelease (used by the desktop update check). | [`tools/asset-manifest/README.md`](tools/asset-manifest/README.md) |
| [`tools/screenshot-gen`](tools/screenshot-gen/README.md) | Boots every ZIP in Hatari on a virtual display and captures preview screenshots into `MARCER_OUT_DIR`; entry kinds are `game`, `desktop`, `textscreen`, `darkscreen`,
`no_game_image` (offline `reclassify` pass; offline `cleanup-duplicates` pass removes pixel-exact duplicate candidates, updates index + metadata and prints a 10-second progress line; offline `promote-app-screens` pass scans `desktop` candidates backwards (skipping TTP dialogs, GEM file windows, blank screens and the plain desktop) and promotes the remaining app screen, resetting TTP-only entries to desktop/desktop; drive-LED resets re-captured via
`run --retry-drive-led`; entries ending as `no_usable_shots` keep the earlier captures as `_cNN` candidates — gated on `keep_candidates` — and use the last capture as preview; old titles that hang on TOS 1.04 are re-captured via `run --retry-no-usable --tos 1.02` (a success records a sparse `tos: "1.02"` marker shown as a `TOS 1.02` badge in the gallery/desktop app, failed attempts go to `tos_tried`); the root/patch overlay merge is case-insensitive for file **and** folder names, so each directory has exactly one canonical output spelling; processing happens in named **scopes** — one scope per invocation via `--scope`, default `cracked` on `index.json`, the opt-in `utils` scope (`Title Sorted/Utilitys - Title Sorted`) on `index-utils.json`, the opt-in `pd` scope (`Title Sorted/PD Games - Title Sorted`) on `index-pd.json`, the opt-in `magazine` scope (`Bonus/Magazine Cover Disks`, scope-local `exclude_dirs: ["dupes"]`) on `index-magazine.json`, the opt-in `falcon` scope (`Falcon 030/Title Sorted`, own TOS 4.04 + Falcon profile, GEMDOS titles extracted and autostarted with `-d`/`--auto`; the static TOS 4.04 boot screens (Atari logo, plain green Videl stage) are detected/rejected before preview selection and removed from older shots via the offline `cleanup-boot-logo` pass) on `index-falcon.json`; monitor mode comes from the gameinfo `screen_format` rules (`MARCER_DATA_DIR/gameinfo/games-<scope>.json`: utils mono unless `Not Mono`/`Low`/`Mid`, including utils entries without a gameinfo match, pd mono only for all-`High` folders) with the `mono_dir_suffix` folder check as fallback; mono boots Hatari `--mono --tos-res high` (ST high res 640x400), and the rules affect future captures only). | [`tools/screenshot-gen/README.md`](tools/screenshot-gen/README.md), [`SPEC-screenshot-generator.md`](docs/specs/SPEC-screenshot-generator.md) |


**Catalog-data pipeline (no screenshots required):** `tools/catalog-update/run.sh`
runs the whole local flow once: FTP sync → `gameinfo-gen` → `full-index-gen` →
`crew-analysis` → gated `asset-publish` upload. Individual steps remain
available as `tools/gameinfo-gen/run.sh extract` (normal `games-*.json`) →
`tools/full-index-gen/run.sh run` (`gameinfo/full-index.json.gz`) →
`tools/crew-analysis/run.sh` (`crews.json`) → `tools/asset-publish/run.sh
publish --only gameinfo` (deterministic `gameinfo-*.zip`; add `--upload` to
send it to the FTP and update `latest.json`).

`tools/screenshot-gen` runs separately on the dev machine; its `index*.json`
and PNGs are uploaded only after new screenshots were captured. The desktop
app merges the gameinfo full index (ZIP universe + hashes) with the screenshot
index (status/kind/preview), so new ZIPs are visible immediately without
waiting for screenshots. Precomputed hashes give exact PirateFinder matches
without decoding ZIPs at runtime.

## 🚀 Release Process

Releases are automated via GitHub Actions. This is a monorepo with **one tag scheme per app** so each app is built and released independently:

| App | Tag scheme | Workflow | Artifacts |
|---|---|---|---|
| Console launcher (`apps/marcer_console/`) | `vX.Y.Z` (e.g. `v0.9.8`) | [`release.yml`](.github/workflows/release.yml) | `MarcerGameDvdConsole-v…-{win,linux,osx}-x64.zip` |
| Flutter desktop (`apps/marcer_desktop/`) | `desktop-vX.Y.Z` (e.g. `desktop-v0.1.0`) | [`desktop-release.yml`](.github/workflows/desktop-release.yml) | `MarcerDesktop-v…-{win,linux,osx}-x64.zip` |

Each workflow triggers only on its own tag prefix (`v*` never matches `desktop-v*` and vice versa), so a desktop release never rebuilds the console launcher and the other way around. Path-based CI (build + test on `main` and PRs, **no release**) runs only when the relevant app changed: [`ci-launcher.yml`](.github/workflows/ci-launcher.yml) for `apps/marcer_console/**`, [`ci-desktop.yml`](.github/workflows/ci-desktop.yml) for `apps/marcer_desktop/**`.

**To create a release:**

You can use the `/create-release` command (via opencode) for a fully automated flow:

```text
/create-release 1.0.0            # console launcher → v1.0.0
/create-release desktop 0.1.0    # Flutter desktop  → desktop-v0.1.0
```

This command validates the version, checks for uncommitted changes, generates a release summary from recent commits, creates a release commit with the summary as the commit message, tags it, and pushes — all in one step. The matching GitHub Action then builds platform ZIPs and creates the GitHub Release.

**Manual release:**
1. Ensure `README.md` and `AGENTS.md` are up to date.
2. Commit all changes.
3. Tag and push (console example):
   ```bash
   git tag v1.2.3
   git push origin v1.2.3
   ```
   Desktop example:
   ```bash
   git tag desktop-v0.1.0
   git push origin desktop-v0.1.0
   ```
4. The matching workflow builds platform ZIPs, generates release notes, and creates a GitHub Release.
