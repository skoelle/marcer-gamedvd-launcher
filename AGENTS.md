## Module Overview (Marcer GameDVD Launcher)

The implementation is split into focused modules (files) under the `apps/marcer_console/` folder (the console launcher is now a legacy/secondary app; the primary application is the Flutter desktop app under `apps/marcer_desktop/`). Keep this section up to date when files are added, removed or responsibilities change.

- apps/marcer_console/Program.cs: Minimal entry point. Sets the console title (via `DefaultTitle` constant) and starts the application by creating `LauncherApp`.
- apps/marcer_console/LauncherApp.cs: Application lifecycle host — loads configuration, initializes components and runs the main directory navigation loop (contains `AppHost` internal class). Key-handling logic is delegated to `InputController`.
- apps/marcer_console/AppConfiguration.cs: POCO configuration classes (`AppConfig`, `AppHatariConfig`, `AppColorConfig`) used to deserialize `launcher.config.json`; color values resolved via `Enum.TryParse<ConsoleColor>` with default fallback.
- apps/marcer_console/ProgramHelpers.cs: Small shared helpers (resolve relative paths, centralized console message helper, input buffer flushing) used across modules.
- apps/marcer_console/OverlayDirectoryBrowser.cs: Filesystem overlay and browsing logic — merges root and patch directories, enumerates folders and ZIPs, protects against path traversal and ensures navigation cannot leave the configured roots.
- apps/marcer_console/NavigationController.cs: Encapsulates selection, scrolling and relative-path navigation logic (cursor, page up/down, per-directory remembered selection/state); uses named scroll-fraction constants.
- apps/marcer_console/MenuRenderer.cs: Console rendering logic — efficient per-line redraw, double-buffering, configurable color selection via injected `AppColorConfig`, and the help box overlay.
- apps/marcer_console/InputController.cs: Handles key events (arrow keys, Enter, Backspace, PageUp/Down, `*`, `?`, ESC, RightArrow) and the associated navigation/drawing logic; owns `ReloadGameEntries` and the virtual `Favorites` folder integration.
- apps/marcer_console/HatariLauncher.cs: Responsible for validating the Hatari executable and starting Hatari with the configured argument template (replaces `{cfg}` and `{zip}`). Exposes `DefaultConfigFile` constant (`MarcerGameDvd-Hatari.cfg`).
- apps/marcer_console/FavoritesService.cs: Manages the favorites/bookmark system — toggling favorites on ZIPs, persisting them to `favorites.txt` (via `DefaultFileName` constant), and providing the virtual `Favorites` folder view (via `FavoritesRootName` constant).
- apps/marcer_console/UIErrorService.cs: Centralized UI error presentation using the console message helper.

Tooling (Python, not part of the launcher build; paths via git-ignored `local/paths.env`, run via each tool's `run.sh` with the repo `.venv`):
- tools/gameinfo-gen/: Extracts the normal game metadata from the GameDVD XLS workbooks into `<MARCER_DATA_DIR>/gameinfo/` (`games-*.json` + manifest/report; it does not build crew data). Run before `tools/crew-analysis` (see `docs/ANALYSIS-game-data.md`).
- tools/crew-analysis/: Ranks cracked-game crews/scene groups by direct release ZIPs (crew view). Reads the `games-cracked.json` produced by `tools/gameinfo-gen` (run that first) and joins the `Crew Sorted` tree with the full `Title Sorted` ZIP list and `games-cracked.json`, uses a curated `aliases.json`/`exclude.txt` registry, prefers `crew` over `cracked_by`, keeps joint credits separate and writes the runtime `crews.json` (all groups + per-release metadata) into `<MARCER_DATA_DIR>/gameinfo/` plus ranking/audit files to `local/crew-analysis/`. `images` additionally suggests cracktro card images by pHash-clustering repeated screens per crew (generic cross-crew/plain-desktop screens filtered) and can seed `crew-images.json`; curated overrides live in `manual-images.json` and are merged by `--write-images`; `crew-tab.json` controls the tab selection (`include_until`/`keep`/`exclude`; `crews.json` carries `"excluded": true`); the app prefers curated `crew-images.json`, then the best release screenshot, then a group icon (see `docs/ANALYSIS-crews.md`).
- tools/atarilegend-gen/: Downloads the weekly AtariLegend MariaDB dump and matches it against the screenshot-index folders. `fetch`/`match`/`report`, plus `extract` (full `atarilegend.sqlite` mirror with a `folders` match map `(section,letter,folder) → al_game_id`, `_meta`, `_table_stats` — tool-side analysis only), `index` (compact runtime index: folders + developer/author/genre facets) and `detail`/`fixtures` (assembled "AtariLegend details" payload incl. derived `atarilegend.com` URLs — reference for the app parser). stdlib parser + built-in `sqlite3`; output to `MARCER_ATARILEGEND_DIR`. AtariLegend data is CC BY-NC-SA 4.0 and is never redistributed in the repo/release (see `docs/ANALYSIS-atarilegend.md`).
- tools/piratefinder-gen/: Fetches the weekly Pete Clarke Greaseweazle PirateFinder Catalog (read-only SQLite, CC BY-NC-SA 4.0) from its GitHub release, verifies the SHA-256 and extracts the Atari ST subset into compact JSON; `fetch`/`extract`/`match`/`report`. `match` decodes `.msa`/`.st`/`.stx` members of the direct cracked-release ZIPs, looks their hashes up in the catalogue (`images`: SHA-1/MD5/SHA-512/CRC32+size) and falls back to normalised title + ZIP cracker/part + gameinfo metadata; reports unambiguous matches, ambiguous candidates, menu-disk appearances, crew-label coverage/aliases and gameinfo gaps. Output to `MARCER_PIRATEFINDER_DIR` (default `local/piratefinder/`); the raw database and all derived files stay local and are never redistributed (see `docs/ANALYSIS-piratefinder.md`).
- tools/gallery/: Interactive gallery webapp over the screenshot archive joined with game metadata (see `docs/SPEC-gallery-webapp.md`); replaces the former static `shotgen html` gallery. Display rules are at parity with the desktop app (preview/thumb preference `done` + `kind: game` with the single game-shot card, per-section screenshot indices — cracked `index.json` plus `index-pd.json`/`index-utils.json`/`index-magazine.json`/`index-falcon.json`; pd/utils cards are the union of their index groups and gameinfo-only folders, with a status filter defaulting to the configured `default_status` (`with_screenshot`) plus the strict `desktop text`/`desktop black` ZIP-level presets and a `pd` TOS/Bad filter — `pending` filter/status segment over any ZIP, section-aware `N folders`/`M with screenshot`/`done <games> (<zips> zips)` statistics plus `gameinfo N folders`/`N without gameinfo` with right-aligned version, combined sort+order dropdown, `?` help overlay, depth-first filmstrip (direct-folder ZIPs before subfolder ZIPs, then screenshot-first) with header badges and clickable crew/cracker groups, **This ZIP** (with the `Kind` row) before the release-variant table, metadata-only boxscan/manual counts and edition/manual labels in the lightbox from `MARCER_ROOT_DIR`/`MARCER_PATCH_DIR` (directory listings + ZIP central directories only; no media served, extracted or downloaded), tab labels `games`/`pd`/`utils`/`magazines`/`falcon`/`crews` (the last tab lists the top 128 non-excluded groups from `<MARCER_DATA_DIR>/gameinfo/crews.json` with curated/release previews; a crew card opens a release browser with screenshot grid, compact release panel, search/sort/keyboard navigation and an `Enter`/double-click game-lightbox link), **no hover info on touch/mobile** — the hover info panel and sticky `:hover` highlights only activate on hover-capable pointers (`(hover: hover) and (pointer: fine)` / `@media (hover: hover)`).
- tools/asset-manifest/: Lists the newest `screenshots-*.zip` / `gameinfo-*.zip` on the Marcer FTP (read-only: connect + list, never uploads) and publishes a small `latest.json` pointer as a **GitHub release asset** on a fixed tag (`catalog-latest`, a prerelease so it never takes the "Latest" slot and never triggers a build), via `gh release upload --clobber` so it can be replaced anytime independently of `desktop-v*` releases; credentials + tag/repo come from the git-ignored `local/paths.env` (`MARCER_FTP_*`, `MARCER_RELEASE_TAG`, optional `MARCER_REPO`). Output schema: `schema`, `generated_at`, `remote`, `screenshots`/`gameinfo` `{archive,size[,sha256]}` (see `tools/asset-manifest/README.md`).
- tools/screenshot-gen/: Generates preview screenshots via Hatari on a virtual display and classifies them (entry `kind`: `game`, `desktop`, `textscreen`, `darkscreen`, `no_game_image`; offline `reclassify` pass; pixel-exact duplicate candidates removed via the offline `cleanup-duplicates` pass, which keeps the preview/first occurrence, updates index + metadata and prints a 10s progress line; application screens of `desktop` entries promoted to the preview via the offline `promote-app-screens` pass (reverse scan skips TTP command-line dialogs, GEM file/drive windows, blank screens and the plain TOS desktop, then swaps the remaining app screen like the app's `M` and sets done/game; TTP-only entries are reset to desktop/desktop instead); drive-LED resets re-captured via `run --retry-drive-led`; entries ending as `no_usable_shots` keep the earlier captures as `_cNN` candidates — gated on `keep_candidates` — and use the last capture as preview). Before `run`, the tool creates its `tmp_dir`, terminates orphaned `hatari`/`Xvfb` helpers from a crashed run (matched by the tool's `tmp_dir` path / display range, independent of their parent process), removes stale `entry-*` staging dirs, checks free disk/RAM and caps `--jobs` from `MemAvailable` + `SwapFree` (`resource_limits`; a worker settles at 0.6-0.8 GB, so `per_job_mb` defaults to 800 to avoid an OOM-killed run, backed by a per-process `mem_guard_fraction` RSS guard). Long parallel runs also cap glibc malloc arenas (`MALLOC_ARENA_MAX=2` via `run.sh`) and call `malloc_trim(0)` per entry. The actual long-run OOM was a cyclic FAT12 chain in the auto-retry floppy scan: a damaged disk whose chain loops back made `chain()`/`parse()` loop forever and grow RAM until the OOM killer reaped the process (e.g. the STX "Fleetstreet Publisher Fonts" disk); `chain()` now stops at the first repeated cluster (cap 4096), directory recursion is depth- and visited-bounded, and the decoders honour `STOP_EVENT` (`SHOTGEN_DIAG=1` writes all-thread stack snapshots/tripwire, `SHOTGEN_TRACEMALLOC=1` dumps allocation sites). **TOS override / 1.02 retry**: `run --tos <version>` boots with another TOS image (config `tos_default` + `tos_images` version→env map; TOS 1.04 = `MARCER_TOS_IMG`, TOS 1.02 = `MARCER_TOS102_IMG`), intended for old titles that hang on 1.04 (black → `no_usable_shots`) — `run --retry-no-usable --tos 1.02`; a successful non-default capture marks the entry (`tos: "1.02"`, sparse, absent = default; metadata always carries `tos`), a failed attempt is remembered in `tos_tried` and skipped next time unless `--force` (§7.5). Works in named **scopes**: one scope per invocation (`--scope`, default `scope_default` = cracked), each with its own tree list and index file — default scope → `index.json` (read by gallery/desktop), other scopes → `index-<name>.json` (e.g. opt-in `utils` scope `Title Sorted/Utilitys - Title Sorted` → `index-utils.json`, opt-in `pd` scope `Title Sorted/PD Games - Title Sorted` → `index-pd.json`, opt-in `magazine` scope `Bonus/Magazine Cover Disks` with scope-local `exclude_dirs: ["dupes"]` and `boot: "auto"` (ST Computer GEMDOS archives extracted + `-d`/`--auto`) → `index-magazine.json`, opt-in `falcon` scope `Falcon 030/Title Sorted` with its own TOS 4.04/profile (GEMDOS titles extracted + `-d`/`--auto`; the static TOS 4.04 boot screens (Atari logo, plain green Videl stage) are detected/rejected before preview selection and removed from older shots via the offline `cleanup-boot-logo` pass) → `index-falcon.json`); no "all scopes" mode (see `docs/SPEC-screenshot-generator.md` §4.4). Monitor mode is resolved before boot: optional gameinfo `screen_format` rules (`MARCER_DATA_DIR/gameinfo/games-<scope>.json`; utils = mono unless `Not Mono`/`Low`/`Mid` hints, including folders missing from a loaded gameinfo file, pd = mono only when all variants are `High`) win over the `mono_dir_suffix` folder check (default `Mono`, matched against the game folder, subdirs included); mono is booted with `--mono --tos-res high` and recorded as `monitor: mono`, and the rules affect future captures only (§4.6). Desktop retry (`detect` + `run --retry-desktop`, click) and the click-free `run --retry-desktop-auto` (scan GEMDOS archives or FAT12 floppies incl. `.stx`/Pasti for the largest/AUTO program and boot with `--auto`, SFX skipped) checks the probe for an already-open GEM window (`find_fullsize_xy`/`find_scroll_down_xy`), skips the drive click and enlarges that window; without an open window it clicks DISKSTATION A, checks the PRG icon first and only then enlarges/scans PRG → folder → scroll; a TTP command dialog is cancelled via ABBRUCH and the next PRG icon in the same window is tried (§7.4).

Docs: `docs/` holds the specs, analysis and decision records (`SPEC.md`, `ANALYSIS-game-data.md`, `ANALYSIS-crews.md`, `ANALYSIS-atarilegend.md`, `ANALYSIS-piratefinder.md`, `ANALYSIS-boxscan-manual-structure.md`, `DECISION-app-architecture.md`, `SPEC-gallery-webapp.md`, `SPEC-screenshot-generator.md`, `BUGS.md`) plus the release setup guide (`GETTING-STARTED.md`) and the living desktop backlog (`IDEAS.md`); indexed by `docs/README.md` plus `docs/images/` (screenshots linked from the README). `README.md` and `AGENTS.md` stay at the repo root.

Apps (Flutter desktop, not part of the C# launcher build; plan in `apps/marcer_desktop/PLAN.md`, decision in `docs/DECISION-app-architecture.md`):
- apps/marcer_desktop/: Flutter desktop app (Surface A inventory browser, later Surface B couch mode). Executable/app bundle `MarcerGameDVDLauncher` (Dart package name stays `marcer_desktop`); app icon generated from the gallery favicon via `tool/generate_icons.py`. Config via git-ignored `desktop.config.json`, searched in CWD → executable dir → (macOS) `.app` parent → (macOS) `~/Library/Application Support/MarcerGameDVDLauncher` (the last-resort writable fallback for a read-only/translocated `.app`); window starts **maximized** via `window_manager` (`Window.maximized`, default true; `false` uses `Window.width/height`, centered); release ZIPs ship `desktop.config.example.json` and the bundled `MarcerGameDvd-Hatari.cfg`. An in-app **settings editor** (⚙ gear left of the Folders button, `lib/widgets/settings_dialog.dart`) edits all path fields (`RootDirectory`, `PatchDirectory`, `ScreenshotDirectory`, `GameinfoDirectory` (the data directory), `Hatari.Executable`, `Hatari.ConfigFile`) with native file/dir pickers (`file_picker`) plus the free-text FTP fields (`Ftp.Host`, `Ftp.User`, `Ftp.Password`, `Ftp.RemoteBase`, `Ftp.AssetsRemote`), writes them back to the same `desktop.config.json` (`DesktopConfig.save`/`copyWith`) and reloads the catalog in place (`HomePage._applyConfig`). Both the editor and the **first-run setup page** (`lib/widgets/setup_page.dart`, shown when no config is found — it lists the searched `desktop.config.json` locations and the save target; an unreadable config gets an error page with a `Setup…` button) share `lib/widgets/settings_form.dart`, which validates every path live (green ✓ / red ✗ per field, no icon for empty optionals) and gates **Save** until all fields are valid (`RootDirectory` is the only required one; a filled-but-invalid optional also blocks). **Data layout:** `GameinfoDirectory` is the data directory: gameinfo files live in `<GameinfoDirectory>/gameinfo/`, the AtariLegend cache in `<GameinfoDirectory>/atarilegend/`, and PirateFinder-Catalog data in `<GameinfoDirectory>/piratefinder/` (screenshots stay in `ScreenshotDirectory`). On startup `lib/data_layout_migration.dart` moves legacy root-level gameinfo files into `gameinfo/` and a legacy configured `AtariLegendDirectory` into `atarilegend/` (target wins, source stays; rename with copy+delete fallback); `AtariLegendDirectory` remains parsed as a legacy read fallback but is no longer shown in the form. A new config is written to the first writable candidate of `configSaveDirs` (exe dir / macOS `.app` parent, CWD, then the macOS per-user data dir) via `writeFirstWritable`. Run via `apps/marcer_desktop/run.sh` (needs Flutter SDK in `~/flutter` and the Linux desktop toolchain). **macOS is not sandboxed** (`macos/Runner/DebugProfile.entitlements`/`Release.entitlements` set `com.apple.security.app-sandbox = false` plus the Flutter hardened-runtime entitlements; `lib/main.dart` calls `FilePicker.skipEntitlementsChecks()` so the native picker works without the user-selected entitlement; `macos/Runner/Info.plist` carries TCC usage strings; downloaded artifacts go to `~/Library/Application Support/MarcerGameDVDLauncher` outside the bundle, which is also the last-resort config save/search location (`config_locator.dart` `extraDir`), and an App-Translocation check (`lib/app_paths.dart` `isAppTranslocated`) shows a startup hint) — the portable launcher reads arbitrary game dirs, writes favorites/index, launches Hatari and self-updates its bundle, none of which the sandbox allows; the release build is ad-hoc signed and **not notarized** (Gatekeeper workaround documented in the README) — see `docs/DECISION-macos-distribution.md`. Default view is the gallery-style catalog grid with a gallery-style detail sidebar; optional overlay folder browser (`T`); **Crews tab** (last tab; curated crew selection (currently 60 groups, cap 128) by direct release ZIPs from `<GameinfoDirectory>/gameinfo/crews.json`, generated by `tools/crew-analysis`; searchable, curated `crew-images.json` cracktro image → best-release-screenshot → group-icon card image, detail panel lists all releases without screenshots and a release click opens the existing lightbox pinned to that cracked card; when the crew matches a PirateFinder-Catalog crew (by name/alias, `CatalogController.pirateFinderCrewForGroup`), the detail panel also shows its members, history, release count and source (no links, no founded); double-clicking a crew card opens the crew release browser — responsive screenshot grid (up to 4 columns) on the left, the normal lightbox sidebar for the selected ZIP on the right, arrow/PgUp/PgDn navigation, Enter opens the normal lightbox, P/Space/Play launches); on desktop, scrollbars stay visible whenever a view overflows (`ScrollbarThemeData.thumbVisibility`). The catalog is index/gameinfo-only (no filesystem scan): ZIPs present locally but absent from the artifacts show only in the overlay browser (`T`), and the `ROOT`/`PATCH`/`BOTH` badges are resolved from the local filesystem, not the published index layer (see `docs/DECISION-catalog-data-source.md`). Loading is robust: a malformed/truncated `games-*.json` is skipped with a warning (never aborts the load), `CatalogController.init` catches failures and shows an error/Retry+Settings screen instead of an endless spinner, and when a section has no cards because the artifacts are missing a banner (`CatalogController.catalogDataNotice` → `main.dart`) points to the settings "Download from FTP" and the status filter `any`. Gallery-style global filters (facet dropdowns with type-to-filter; all filter dropdowns (facets, status, sort, raw/pasti/boxscan, TOS/Bad) use a custom virtualized `MenuAnchor` + `ListView.builder` picker (type-to-filter plus Up/Down/Enter navigation; only visible rows are built, so ~1,000-entry lists open instantly) and the filter bar rebuilds only when `CatalogController.filterRevision` changes, not on selection or async-scan notifications; **app-only** additionally **Genre** and **Developers** from the AtariLegend cache and a **Publisher** facet that merges gameinfo + AtariLegend publishers) + card universe (`GameCard`/`CatalogFilter` in the catalog package), fuzzy crew/cracker focus (crew/cracker groups in the detail sidebar and lightbox info panel are clickable → open that group's ZIP), lightbox (integer scaling, depth-first filmstrip/variant table — direct-folder ZIPs before subfolder ZIPs), favorites (`*` toggles the selected card's/ZIP's favorite in both views — for a card its single starred variant, else the launch ZIP; `FAVORITE` badges, per-thumb ★/☆ stars in the lightbox filmstrip, `★ Favorites` catalog filter listing favorites of the **active section** with facets/status ignored, plus one virtual `Favorites` folder per section in the browser, any-ZIP cards count as favorite, lazy pd/utils ZIP resolution; stored **per section tree** in `favorites.txt` under `<Patch>/<tree>/` as root-relative POSIX paths — portable console layout — plus legacy `favorites.txt` (section-classifiable entries migrated into their section file on load; legacy absolute Windows/Linux paths rewritten relative; paths outside every tree and unresolvable foreign lines stay put, timestamped `.bak-*` before rewrite), see root README), and **Hatari launch** (`P` / `Space` / Play button, `{cfg}`/`{zip}` substitution, bundled-cfg fallback, non-blocking; the **PLAY** button is a split button with a variant dropdown — Standard (ST, TOS 1.04), Mono (`--monitor mono`), STE (`--machine ste`, TOS 1.62 → `TOS162.IMG`), Low Res TOS 1.02 (`TOS102.IMG`) and Low Res TOS 1.00 (`TOS100.IMG`); `kHatariVariants` in `packages/marcer_catalog/lib/src/launch.dart`, extra args appended after the template, variant TOS files downloaded on demand by the pre-launch guard). A card whose index variant carries a non-default `tos` (e.g. `1.02`, from the screenshot generator's TOS retry) shows a deep-orange `TOS 1.02` badge (grid tile/detail/lightbox header), a `TOS` row in "This ZIP", and the primary Play action (`P`/`Space`/Play button) preselects the matching launch variant (`CatalogController.defaultVariantForCard` matches `HatariVariant.tosVersions`; the dropdown still overrides). **Send to CosmosEx** (`CosmosEx` config block; user decision 2026-10-26): when `CosmosEx.Host` is set, the PLAY split-button dropdown gains **Send to CosmosEx** for the currently shown ZIP (card variant, single favorite or browse entry). `CosmosEx.Mode` is `auto` (default: probe legacy first, then cosmo2ex), `legacy` or `cosmo2ex`. Legacy (classic ce-atari) uploads the whole ZIP as multipart field `file` to `POST /api/v1/floppy/0` and activates slot 0 with `PUT /api/v1/floppy/0` (fixed slot, device extracts the first .st/.msa). cosmo2ex has no upload API: the app extracts the first `.st/.msa`, writes it into `CosmosEx.ShareDirectory` (local/SMB/NFS mount of the device's `FLOPPY_IMAGES_DIR`), logs in with `CosmosEx.Password` via `POST /auth/login`, resolves the MAC (`CosmosEx.Mac`, empty = only device from `/devices`), reads `defaultDir` from `GET /fdd/{mac}/image` and inserts `{"image":"<defaultDir>/<file>"}` with `PUT /fdd/{mac}/image`; the self-signed HTTPS cert is accepted for the configured host only. Sent share files use `marcer-<zip-name>-<content-hash>.<st|msa>`. The client lives in `lib/cosmos_ex.dart` (`CosmosExUploader`/`HttpCosmosExUploader`, injectable for tests), the controller exposes `sendSelectedToCosmosEx`/`sendZipToCosmosEx` with status-bar progress, a success snackbar and an error modal (`main.dart`), and the shared settings form is tabbed (Library = paths/FTP/catalog data, Hatari = executable/config/install/TOS, CosmosEx = its own tab after Hatari; mode dropdown, host, password, MAC, share directory; a filled-but-missing share blocks Save; a red dot on a tab marks invalid fields there). Legacy HTTP is unencrypted and the cosmo2ex password is stored in plaintext like the FTP password. **Hatari download/install** (Stufe 1: prebuilt Windows x64 / macOS universal binaries from the official SourceForge project, pinned `kHatariVersion = '2.6.1'`; `lib/hatari_installer.dart`): when no `Hatari.Executable` resolves to an existing file, the chained pre-launch guard (`HomePage._beforeLaunch` → `_ensureHatari` **before** `_ensureTos`) offers an install dialog (`lib/widgets/hatari_install_dialog.dart`) that downloads + unpacks into `<appDir>/hatari` (Windows/Linux) or `~/Library/Application Support/MarcerGameDVDLauncher/hatari` (macOS — outside the `.app` bundle, via `lib/app_paths.dart` `downloadedDataDir`, because a quarantined app runs from a randomized read-only App-Translocation path where bundle writes do not survive), locates the executable (`hatari.exe` / macOS `Hatari.app/Contents/MacOS/hatari` / plain `hatari`), `chmod +x`, strips the macOS download quarantine, writes the path back into `desktop.config.json` (relative to the app dir on the portable Windows/Linux layout, absolute on macOS) and updates the live controller in place (`CatalogController.replaceConfig` — no catalog reload); the shared settings form also has a **Hatari installation** status row with Install/Reinstall (`hatariDownloader`/`hatariBuild` injectable) that fills the `Hatari.Executable` field (`lib/widgets/settings_form.dart`); Linux has no official prebuilt binary (`hatariBuildFor` → `null`) so the row/dialog point to a manual system install. Pure Dart `dart:io` HttpClient + `archive` + `crypto` (optional sha256; SourceForge publishes none so it stays unset). **Self-update** in release builds only (silent startup check against the GitHub `desktop-v*` releases; amber `⬆ <version>` badge left of the Folders button → download platform ZIP, swap-install with `*.old` backup, automatic relaunch — on Linux/macOS the app awaits the detached new process before exiting; version from `--build-name` via `package_info_plus`; dev builds never check; the status bar shows the running app version right-aligned). The extractor preserves **Unix symlinks** (`extractArchiveToDir` recreates `ditto` zip symlink entries — the macOS `Frameworks/*.framework` layout relies on `App` → `Versions/Current/App` and `Versions/Current` → `A`; writing them as files broke the bundle and the app failed to launch; `_copyDir`/`swapInstall`/`_deletePathBestEffort` also handle `Link` entries), and on macOS `swapInstall` is followed by a **framework-link verification** (`verifyMacOsFrameworkLinks`); a broken swap is **rolled back** from `*.old` (`rollbackInstall`) instead of leaving an unstartable app, and the freshly swapped `.app` is **ad-hoc re-signed** (`resignMacOsBundle` → `codesign --force --deep --sign -`). **Windows is two-phase** (in-process rename is blocked by the mapped `data\app.so`/`flutter_windows.dll`): a hidden PowerShell helper waits for the app to exit, then swaps/relaunches; it is started via a **one-shot Task Scheduler task** (`schtasks` `/SC ONCE /IT`, encoded-command wrapper; the app sits in a job object with kill-on-close, so a plain child would die with it — direct detached spawn is only the fallback), and both the app (`UpdateLog`, incl. the exact command line, `currentProcessInJob()` via FFI and a 700 ms stdout/stderr drain) and the helper log to `MarcerUpdater.log` next to the app; the log path is shown in the failure dialog. **Manual screenshot curation** (lightbox `M` = swap shown candidate ↔ main image on disk, refreshing grid/detail/filmstrip/candidate strips immediately via per-path `imageVersionOf` + `ValueKey` image keys **plus** an `imageCache.clear()` + `clearLiveImages()` flush — `clear()` alone keeps `_liveImages`, which `putIfAbsent` consults, and would hand the old completer back during the rebuild — `CatalogController.swapPreviewImage`; # Requirements for the Marcer GameDVD Launcher (AGENTS.md)

## Basic Function / Purpose
The console launcher is meant for browsing a games directory and can launch ZIP files with the Hatari emulator. It runs on Windows, Linux, and macOS. Control is exclusively via keyboard in the console window.

## Detailed Requirements

### Navigation and Display Principles
- Start directory (root):
  The configured RootDirectory from launcher.config.json
  It must NEVER be possible to navigate outside this directory.
- Only display subfolders and ZIP files; ignore other file types and hidden files.
- Navigation and control exclusively with these keys:
  - Arrow down/up: scroll by single entries
  - Enter / RightArrow: open folder or launch ZIP with Hatari
  - Backspace / LeftArrow: jump to parent directory (never outside root)
  - ESC: exit the program
  - PageUp/PageDown: jump by one page up/down through the file list
  - `?`: show a help box with key bindings
- The file list always shows exactly as many lines as fit the screen – ALWAYS **one line less** than the console height (`Console.WindowHeight - 1`). This avoids overflow at the bottom and ensures the selection never enters the non-visible area.
  Rationale: writing to the very last console line can cause the Windows console to auto-scroll or produce visual jumps when the cursor reaches the bottom row. Reserving one line prevents unintended scrolling/flicker and keeps the selection cursor strictly within the visible area.
   Maintenance: when changing rendering or navigation logic, always compute the displayed page size as `availableLines = ProgramHelpers.AvailableLines` (which resolves to `Console.WindowHeight - 1`) and keep this value consistent across MenuRenderer, NavigationController and any other code that references the console height.
- There is no information line/path display.
- Cursor and scroll logic:
  - The selection cursor must always remain in the visible area.
  - If the list is longer than the visible window, scrolling is necessary (cursor moves to bottom/top third as you move through).
- The program may be started in the root directory; all subfolders/ZIPs should be accessible from there.

### Launching a Game
- If Enter is pressed on a ZIP, Hatari is called with the configured executable, config file, and the full path to the ZIP file as arguments.
- `Hatari.ConfigFile` is optional. When empty, the bundled `MarcerGameDvd-Hatari.cfg` (shipped with the launcher) is used automatically. The bundled config never starts in fullscreen (`bFullScreen = FALSE`) and uses the SDL renderer with desktop resolution (`bUseSdlRenderer`, `bKeepResolution = TRUE`) so the `F11` fullscreen toggle centers the image and preserves its aspect ratio with black letterbox bars instead of stretching it or drawing it in the top-left corner.

### Error Handling & Edge Cases
- Paths with special characters or spaces must work robustly.
- It must NEVER be possible for navigation logic to leave the configured root folder.
- Empty directories must be displayed correctly (or reported correctly).
- In the root directory, Backspace must have no effect (no error, do not leave the program).
- Navigation (Backspace, Enter, etc.) must remain robust even for very deep or large directory trees.
  - Hatari.Executable is validated during startup: the path is resolved (relative to the EXE directory when applicable) and must point to an existing file. If validation fails the program must present a clear error and exit.

### Miscellaneous
- Build and start scripts live next to the console code: `apps/marcer_console/build.cmd` / `build.sh` / `start.cmd` / `start.sh` and must be used.
 - **Scope: these scripts and this build requirement apply ONLY to changes under `apps/marcer_console/`.** Changes to other apps (`apps/marcer_desktop/`) or to `tools/` do **not** require running the console build — use their own build/run paths (`apps/marcer_desktop/run.sh`, `tools/*/run.sh`).
 - **For ALL console builds and releases, ONLY the platform build script may be used:** `apps/marcer_console/build.cmd` (Windows) or `apps/marcer_console/build.sh` (Linux/macOS). Direct `dotnet build`/`dotnet run` calls are NOT allowed, as they can lead to version/runtime conflicts. The console application must always be started and tested using `apps/marcer_console/start.cmd` (Windows) or `apps/marcer_console/start.sh` (Linux/macOS).
 - **After making any code changes that affect behavior or touch source files under `apps/marcer_console/`, run the platform build script** (`apps/marcer_console/build.cmd` on Windows, `apps/marcer_console/build.sh` on Linux/macOS) and ensure the build completes successfully before committing. Additionally, perform a manual functional test on a Windows, Linux, or macOS machine prior to pushing a release.
- The console window can have any number of lines; display/navigation must adapt dynamically.
- For every release, a Release Notes file must be maintained that summarizes all changes, bugfixes, and new features in that version; Release Notes must be provided with the release asset.
- README.md must be written in English. Any functional change that affects usage, configuration, or behavior MUST update README.md in English immediately after the change. If there are consequential changes to developer-facing policies, build steps, or requirements, AGENTS.md must be updated as well.
- **IMPORTANT:** With any functional change to the launcher, BOTH this file (AGENTS.md) AND the README.md must always be updated and kept current. Immediately after, a successful build must be executed. This is mandatory for all development on the project.

## Layer/Overlay Mode

### Overlay Logic
- The display always combines the contents of the game root ("main directory") and patch directory.
- There is always exactly one overlay browser – at every level, both sources are combined.
- Each folder/file is only shown once per name:
    - If a folder/ZIP exists in both layers, the patch version takes precedence for launching/navigation.
- ZIP start/open always uses the patch file path if present, otherwise from root.
- Navigation combines both layers **recursively** at every sublevel. Navigation/Backspace is always relative.

Note on PatchDirectory semantics:
- PatchDirectory is optional. If the configuration contains no PatchDirectory or it is empty, the application treats this as "no patch layer" and will not consult any patch paths. In other words: an empty or missing PatchDirectory will not implicitly point to the EXE or any other folder — the overlay layer is simply disabled.

Implementation note (input flushing):
- To avoid undesired key-repeat / input "afterglow" when the user holds navigation keys, the application performs a best-effort flush of the console input buffer after navigation events. This is implemented by ProgramHelpers.FlushInputBuffer(), which uses the Win32 FlushConsoleInputBuffer API on Windows. This behaviour is intentional and required to provide a responsive navigation experience.

### Color Scheme and Layer Labels
Each entry is displayed with a left label indicating its layer status:
- **`[BOTH]`**: Entry exists in both main and patch layer
- **`[ROOT]`**: Entry exists only in main (root) layer
- **`[PTCH]`**: Entry exists only in patch layer

Color mapping (now configurable via the `Colors` section in `launcher.config.json`; defaults shown below):
- Folder in both layers: **Yellow** (`[BOTH]`) → `FolderBoth`
- Folder only in patch layer: **DarkYellow** (`[PTCH]`) → `FolderPatchOnly`
- Folder only in main layer: **Gray** (`[ROOT]`) → `FolderRootOnly`
- ZIP in both layers: **Green** (`[BOTH]`) → `ZipBoth`
- ZIP only in main layer: **DarkGreen** (`[ROOT]`) → `ZipRootOnly`
- ZIP only in patch layer: **Magenta** (`[PTCH]`) → `ZipPatchOnly`
- Selected entry foreground: **Black** → `SelectedForeground`
- Selected entry background: **DarkCyan** → `SelectedBackground`
- Virtual entry (Favorites pseudo-folder): **White** → `VirtualEntry`

Note: Color values are resolved in `MenuRenderer` from the injected `AppColorConfig` (populated in `LauncherApp.LoadConfiguration` via `Enum.TryParse<ConsoleColor>` with default fallback). Invalid or missing values fall back to the defaults above. If you change default color values in `AppColorConfig`, update this section and the README color tables to keep documentation and implementation in sync.

### Navigation
- Navigation is always based strictly on the **relative path from root** and is consistent on all levels (Backspace always moves up one level, Enter always moves one level deeper, regardless of which layer).
